# 03. Варианты спецификации

Выбор делается по двум независимым осям: **объём продукта** (что получает клиент) и **архитектура сбора** (как добываем данные). Оси ортогональны — любой пакет можно собрать на любой архитектуре.

---

## Ось 1. Пакеты

### Пакет A — «Сигнал» (Lite)

**Идея:** доказать гипотезу и начать приносить пользу до того, как построен интерфейс.

| Что входит | Что не входит |
|---|---|
| 1 площадка (ПроДокторов — самая массовая и с подтверждённой механикой) | Раздел в дашборде |
| Ежедневный обход, состояния `AVAILABLE / NO_SLOTS / BOOKING_OFF / UNKNOWN` | Фильтры, сортировки, история в UI |
| История в БД, дата начала инцидента | Две другие площадки |
| Ежедневный дайджест в Telegram | Оперативные алерты по одиночным событиям |
| Ежедневная выгрузка XLSX в тот же чат | Mute через интерфейс (только через конфиг) |

**Трудоёмкость:** 16 чел-дней (P80 22) · **Календарь:** 4 недели full-time
**Цена:** 180 000 ₽ внедрение + 12 000 ₽/мес
**Когда брать:** если заказчик сомневается, если нужно быстро показать результат, или как платный пилот перед пакетом B с зачётом стоимости.
**Ограничение:** не соответствует п. 3 состава работ КП (раздел в дашборде). Продавать честно, как пилот.

---

### Пакет B — «Стандарт» (рекомендуемый; состав работ КП + необходимый минимум сверх него)

**Полностью покрывает пп. 1–5 состава работ КП.** Плюс шесть вещей, без которых пункты КП формально выполнены, а продукт не работает.

| Из КП | Добавлено сверх КП | Зачем |
|---|---|---|
| 1. Ежедневная проверка на 3 площадках | Статус `UNKNOWN` отдельно от «записи нет» | Иначе любой таймаут = ложный алерт |
| | Подтверждение 2-из-3 перед сменой состояния на «плохое» | Антифлап |
| | Канареечные точки | Отличить «клиника сломалась» от «мы сломались» |
| 2. Хранение истории, дата пропажи | Склейка инцидентов, устойчивая к `UNKNOWN`-разрывам | Иначе «дата пропажи» будет прыгать |
| | Снапшот-доказательство на момент смены состояния | Снимает споры «а у нас всё работает» |
| 3. Раздел «Онлайн-запись», фильтры, XLSX | Mute / snooze до даты + исключения | Иначе через месяц раздел — свалка отпусков |
| 4. Алерты «пропала / вернулась» | Агрегация: дайджест + порог массовости + дедупликация | Иначе 300 сообщений в одно утро |
| 5. Настройка на данных, приёмка | Формализованная методика приёмки и метрики точности | Иначе приёмка бесконечна |

**Разделение трёх причин** (`SCHEDULE_EMPTY` / `NO_SLOTS` / `BOOKING_OFF`) — **включено в базу.** Формально это сверх КП, но без него самые загруженные врачи клиники будут ежедневно попадать в отчёт как «проблема». Стоит 2 человеко-дня и определяет, доживёт ли раздел до третьего месяца. Подробно — [04-TZ.md §6](04-TZ.md).

**Трудоёмкость:** P50 = 34 чел-дня, P80 = 46 · **Календарь:** 8–9 недель full-time (P80 — 12)
**Цена:** 420 000 ₽ фикс, либо 190 000 ₽ + 42 000 ₽/мес (рекомендуется)

### Пакет C — «Управляемая доступность» (Pro)

Пакет B плюс:

| Блок | Содержание | +чел-дни |
|---|---|---|
| Глубина слотов | Состояние `THIN`, «дней до ближайшего слота», SLA «≤3 дней» | +2 |
| Двусторонняя сверка | Сопоставление «что клиника выгрузила из МИС/шины» с «что видно на площадке» → **автоматическое определение причины** | +5–7 |
| Отчётность руководителю | Еженедельный и месячный отчёт: Booking Uptime, рейтинг филиалов, предотвращённые врачо-дни | +2 |
| Роли и права | Маркетолог / администратор филиала / руководитель; каждый видит своё | +2 |
| API и вебхуки | Отдача состояний наружу, интеграция с хелпдеском клиники | +2 |
| **Итого пакет C** | **34 + 14** | **= 48** |

Опции сверх пакета C, выносимые в roadmap: связка с отчётом о позициях (+3,5), предиктивный алерт по падающей глубине слотов (+4,5). См. [02-PRODUCT.md §5](02-PRODUCT.md).

**Трудоёмкость:** 48 чел-дней (P80 65) · **Календарь:** 12–14 недель full-time
**Цена:** 690 000 ₽ фикс, либо 290 000 ₽ + 68 000 ₽/мес

## Ось 2. Архитектура сбора

### A1 — HTTP-first («реплей запросов страницы»)

Воспроизводим те же запросы, которые делает сама страница площадки: как правило, JSON-эндпоинты за SPA.

| Плюсы | Минусы |
|---|---|
| 20–50× дешевле по ресурсам: обход 900 точек за 5–15 минут на одном ядре | Ломается при смене формата API |
| Данные структурированы — надёжная классификация состояний | Требует рекогносцировки по каждой площадке |
| Ничтожная нагрузка на площадку (соответствует п. 5.3 договора) | Не работает, если ответ подписывается или требует исполнения JS |
| Легко тестируется на сохранённых фикстурах | |

### A2 — Browser-first (Playwright)

Открываем карточку врача в headless-Chromium, ждём рендер виджета, читаем DOM.

| Плюсы | Минусы |
|---|---|
| Работает почти всегда, независимо от внутреннего API | 900 × 6–10 с = **1,5–2,5 часа** машинного времени на 1 воркер |
| Устойчив к смене внутренних форматов при неизменном UI | Требует 4–8 ГБ RAM, параллелизм 4–6 воркеров → 20–35 мин |
| Даёт настоящий скриншот-доказательство | Ломается при смене вёрстки; селекторы хрупкие |
| | Заметно выше нагрузка на площадку — хуже соответствует «щадящему режиму» |

### A3 — Гибрид (рекомендуемый)

```
Ежедневно, все 900 точек:
    L1  bulk-листинг врачей клиники (5–20 запросов на площадку)
        └─ даёт: карточка существует, онлайн-запись вкл/выкл
              │
              ├─ запись выключена / карточки нет  →  состояние определено, дальше не идём
              │
              └─ запись включена  →  L2: запрос календаря слотов по врачу
                                          ├─ успех    → AVAILABLE / THIN / NO_SLOTS / SCHEDULE_EMPTY
                                          └─ неудача  → одна повторная попытка → UNKNOWN

Точечно, Playwright:
    • все точки, оставшиеся в UNKNOWN после L2
    • случайная выборка 5 % «здоровых» точек — ночной аудитор:
      сверяет вывод HTTP-пути с тем, что реально рендерится.
      Расхождение → алерт разработчику, а не клиенту.
    • канареечные точки (см. ТЗ §7.3)
```

**Почему именно так:**

- **L1/L2-эскалация** резко снижает число запросов: если из 300 врачей на площадке у 280 запись включена, календарь запрашиваем 280 раз, а не 300 — но главное, для выключенных не делаем лишнего. При массовом сбое (запись выключилась у всех) L2 вообще не запускается — нагрузка падает, а не растёт. Это ровно то, что обещано в КП: «данные по всем врачам снимаются несколькими запросами».
- **Ночной аудитор** — единственный способ узнать, что HTTP-путь начал врать, до того, как об этом скажет клиент. Стоит 45 запросов в сутки.
- **Playwright как fallback**, а не как основа, даёт устойчивость без платы за ресурсы.

**Стоимость архитектуры:** A3 дороже A1 на 2–3 человеко-дня и дешевле A2 в эксплуатации в 10–20 раз.

### Сравнение архитектур

| | A1 HTTP | A2 Browser | **A3 Гибрид** |
|---|---|---|---|
| Время обхода 900 точек | 5–15 мин | 20–35 мин (6 воркеров) | 10–20 мин |
| Требуемый VPS | 1 vCPU / 2 ГБ | 4–8 vCPU / 8–16 ГБ | 2–4 vCPU / 4–8 ГБ |
| Стоимость VPS | ~1 500 ₽/мес | ~8 000 ₽/мес | ~4 000 ₽/мес |
| Нагрузка на площадку | минимальная | заметная | минимальная |
| Устойчивость к смене API | низкая | высокая | **высокая (fallback)** |
| Устойчивость к смене вёрстки | высокая | низкая | **высокая** |
| Самодиагностика вранья | нет | нет | **да (аудитор)** |
| Трудоёмкость реализации | база | база +1 | **база +2–3** |

## Матрица выбора

| Если... | Пакет | Архитектура |
|---|---|---|
| Заказчик готов, бюджет утверждён, состав работ КП надо выполнить | **B** | **A3** |
| Нужно показать результат за 3 недели / заказчик сомневается | A, с зачётом в B | A1, с расчётом на миграцию в A3 |
| Целимся в продукт для нескольких клиник | B + мультитенантность | A3 обязательно |
| Фаза 0 показала жёсткую защиту на одной из площадок | B | A3, где эта площадка — на A2 |
| Заказчик готов дать доступ к своей стороне выгрузки (МИС/шина) | C | A3 + сверка |

## Рекомендация

**Пакет B на архитектуре A3, с мультитенантностью, заложенной на уровне схемы данных и конфигурации.**

Итоговая трудоёмкость: **34 (база) + 3 (A3) + 7 (мультитенантность) ≈ 44 чел-дня P50**, P80 ≈ 58.

Если бюджет или сроки не позволяют, порядок отказа — строго такой:

1. Сначала отказаться от мультитенантности — **но только письменно зафиксировав, что права на ПО остаются у исполнителя** ([02-PRODUCT.md §2а](02-PRODUCT.md)), иначе путь назад закрыт навсегда.
2. Затем сузить до одной площадки (пакет A) с планом добавления двух остальных.
3. **Ни при каких обстоятельствах не отказываться от:** статуса `UNKNOWN`, канареек, агрегации алертов, mute и разделения трёх причин. Это не улучшения, это условия работоспособности. Продукт без них формально соответствует КП и перестаёт использоваться на третий месяц.
