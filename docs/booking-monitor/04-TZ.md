## 1. Назначение и границы

### 1.1 Назначение

Система ежедневно определяет, может ли пациент записаться к каждому врачу клиники на каждой из трёх площадок (ПроДокторов, НаПоправку, СберЗдоровье), хранит историю этих состояний, показывает их в отдельном разделе дашборда и уведомляет ответственных о пропаже и возврате возможности записи.

Система наблюдает **результат, видимый пациенту**, а не настройку в кабинете площадки.

### 1.2 Что система делает

| | |
|---|---|
| Д1 | Определяет состояние возможности записи по каждой точке мониторинга не реже 1 раза в сутки |
| Д2 | Отличает «врач расписан» от «расписание не выгрузилось» от «онлайн-запись выключена» от «карточки нет» от «проверить не удалось» |
| Д3 | Хранит историю состояний бессрочно и определяет дату начала каждого инцидента |
| Д4 | Показывает актуальную картину в разделе «Онлайн-запись» с фильтрами и выгрузкой в XLSX |
| Д5 | Уведомляет в Telegram о пропаже и возврате записи, агрегируя массовые события |
| Д6 | Ведёт сопоставление реестра врачей клиники с карточками на площадках |
| Д7 | Диагностирует собственную неисправность и отличает её от неисправности у клиники |

### 1.3 Что система не делает (границы)

| | |
|---|---|
| Н1 | Не определяет причину недоступности за пределами классификации §6 — отпуск, сбой конкретной интеграции, действия администратора устанавливает клиника |
| Н2 | Не совершает записей к врачам и не отправляет площадкам никаких данных |
| Н3 | Не собирает сведения о занятых приёмах и о пациентах (п. 11.7 договора) |
| Н4 | Не обходит средства защиты площадок; при появлении блокирующей защиты работа по площадке приостанавливается с уведомлением (п. 5.3 договора) |
| Н5 | Не вносит изменений в кабинеты площадок и в МИС клиники |
| Н6 | Не гарантирует обнаружение недоступности, длящейся менее интервала обхода (менее суток) |
| Н7 | Не заменяет отчёт о позициях и не дублирует его данные |

### 1.4 Глоссарий

| Термин | Определение |
|---|---|
| **Площадка** | Медицинский агрегатор: ПроДокторов, НаПоправку, СберЗдоровье |
| **Карточка** | Публичная страница врача на площадке в контексте конкретного филиала |
| **Точка мониторинга (ТМ)** | Уникальная тройка «врач × филиал × площадка». Единица наблюдения, состояния, истории и алертов |
| **Обход** | Однократный проход по всем активным ТМ. Имеет идентификатор, время начала и окончания, итоги |
| **Проверка** | Однократное определение состояния одной ТМ в рамках обхода |
| **Состояние** | Одно из значений §6.1 |
| **Инцидент** | Непрерывный период нахождения ТМ в «плохом» состоянии, от подтверждённого перехода до подтверждённого возврата |
| **Горизонт (H)** | Число дней вперёд, в пределах которого ищутся свободные слоты. По умолчанию 14 |
| **Канарейка** | ТМ с заведомо исправной записью, используемая для самодиагностики системы |
| **Заглушение (mute)** | Временное исключение ТМ из алертов и из подсчёта Booking Uptime |
| **Booking Uptime** | Доля точко-дней в состоянии `AVAILABLE` от всех незаглушённых точко-дней |
| **Снапшот** | Усечённый сырой ответ площадки, сохранённый как доказательство состояния |

## 2. Цели и критерии успеха

| Цель | Измеримый критерий |
|---|---|
| Ц1. Сократить время обнаружения недоступности | **MTTD ≤ 24 ч** (было — «узнают случайно», оценочно 7–14 дней) |
| Ц2. Не создавать ложных тревог | **Доля ложноположительных ≤ 2 %** на приёмочной выборке и в первый месяц эксплуатации |
| Ц3. Дать полную картину по сети | **≥ 98 %** врачей реестра сопоставлены с карточками на каждой площадке, где клиника представлена |
| Ц4. Обеспечить непрерывность наблюдения | **≥ 99 %** суток с успешно завершённым обходом; доля `UNKNOWN` за обход **≤ 3 %** |
| Ц5. Не нагружать площадки | **≤ 1 запрос/сек** на площадку, обход укладывается в заданное окно |
| Ц6. Быть используемой | Раздел открывается ответственным **не реже 3 раз в неделю** на третьем месяце эксплуатации |

Ц6 — не техническая, а продуктовая цель, и она главная. Все требования по агрегации алертов, mute и различению причин существуют ради неё.

## 3. Роли и сценарии

### 3.1 Роли

| Роль | Кто | Что делает в системе |
|---|---|---|
| **Оператор клиники** | Маркетолог / старший администратор | Смотрит раздел, фильтрует, выгружает XLSX, заглушает известные отсутствия, получает алерты |
| **Руководитель** | Коммерческий директор / владелец | Смотрит сводку и Booking Uptime, получает недельный отчёт |
| **Администратор системы** | Исполнитель | Управляет реестром и сопоставлением, порогами, канарейками, каналами уведомлений |
| **Разработчик** | Исполнитель | Получает технические алерты, чинит коннекторы, ведёт runbook |

### 3.2 Ключевые сценарии

**С1. Утренняя проверка (оператор, ежедневно, 2 минуты).**
Приходит дайджест → видит «новых инцидентов: 4» → открывает раздел по ссылке → раздел отсортирован по «дней в состоянии» по убыванию → видит 4 новых сверху с пометкой «новое» → по каждому видит филиал, площадку, класс причины и подсказку «что проверить» → передаёт администратору филиала или в ИТ.

**С2. Массовый сбой (оператор, срочно).**
В 09:22 приходит срочное сообщение: «Массовая пропажа записи. СберЗдоровье, филиал Ленина 5: 34 из 38 врачей. Признак: расписание не выгружено. Похоже на сбой выгрузки из МИС». Одно сообщение вместо 34. Оператор сразу идёт в ИТ, а не разбирает список врачей.

**С3. Заглушение известного отсутствия (оператор, по факту).**
Видит «Сидоров С.С. — нет записи, 3 дня». Знает, что врач в отпуске до 15 сентября. Нажимает «Заглушить до…», выбирает дату, пишет причину «отпуск». ТМ уходит из списка активных, из алертов и из знаменателя Booking Uptime. 16 сентября автоматически возвращается в наблюдение; если запись не вернулась — попадает в дайджест как новый инцидент.

**С4. Расследование (оператор, при споре).**
Администратор филиала говорит «у нас всё включено». Оператор открывает карточку ТМ → видит историю состояний по дням, дату и время каждой проверки, ссылку на карточку врача на площадке и снапшот-доказательство на момент перехода. Спор закрыт за 30 секунд.

**С5. Ремонт коннектора (разработчик, при смене механики площадки).**
Ночной аудитор фиксирует расхождение HTTP-пути и браузерного рендера ИЛИ ≥50 % канареек площадки одновременно «упали». Обход по площадке помечается `SUSPECT`, состояния не обновляются, алерты клиенту по этой площадке подавляются, разработчику приходит технический алерт. Разработчик по runbook снимает свежие фикстуры, чинит коннектор, прогоняет golden-тесты, выкатывает, запускает внеочередной обход.

**С6. Новый врач (администратор, еженедельно).**
В листинге площадки появилась карточка, не связанная ни с одним врачом реестра → попадает в очередь «Новые карточки». Администратор связывает или помечает «не наш».

## 5. Требования к сбору данных

### 5.1 Общий интерфейс коннектора

Каждая площадка реализует один интерфейс. Добавление четвёртой площадки не должно затрагивать ядро.

```python
class PlatformConnector(Protocol):
    code: str                       # 'prodoctorov' | 'napopravku' | 'sberhealth'

    def capabilities(self) -> Capabilities:
        """Что площадка позволяет различить.
        distinguishes_empty_schedule: bool  — отличима ли Р1/Р2 (пустой календарь)
                                              от Р6 (все слоты заняты)
        supports_bulk_listing: bool         — есть ли листинг врачей клиники
        max_horizon_days: int               — предел горизонта площадки
        """

    async def list_cards(self, clinic_ref: ClinicRef) -> list[CardRef]:
        """L1: перечень карточек врачей клиники с внешними ID,
        филиалом и признаком включённости онлайн-записи."""

    async def fetch_availability(self, card: CardRef, horizon_days: int)
            -> RawAvailability:
        """L2: сырые данные календаря по карточке.
        Возвращает СЫРОЕ представление, не состояние — классификация
        вынесена в §6 и общая для всех площадок."""
```

**Требование:** коннектор **не** возвращает готовое состояние. Он возвращает нормализованные факты (карточка найдена / запись включена / список дней календаря / список свободных слотов по дням / признак «календарь пуст»). Классификация — единый код на все площадки. Это гарантирует, что три площадки классифицируются одинаково и что правило меняется в одном месте.

### 5.2 Схема эскалации L1 → L2 (архитектура A3)

```
для каждой площадки:
    L1: list_cards(clinic)                       # 5–20 запросов на всю клинику
        для каждой ТМ:
            карточка отсутствует в листинге  →  CARD_MISSING   (L2 не нужен)
            онлайн-запись выключена          →  BOOKING_OFF    (L2 не нужен)
            онлайн-запись включена           →  в очередь L2
    L2: fetch_availability(card, H)  для каждой ТМ из очереди
        успех                                →  классификатор §6
        неудача                              →  1 повтор → UNKNOWN → очередь Playwright
```

Эффект: при массовом сбое (запись выключилась у всех) L2 не запускается — нагрузка на площадку падает, а не растёт. Это соответствует обещанию КП «данные по всем врачам снимаются несколькими запросами».

### 5.3 Ограничения нагрузки (реализация п. 5.3 договора)

| Параметр | Значение по умолчанию | Настраивается на площадку |
|---|---|---|
| Максимальная частота | **1 запрос/сек на площадку** | да |
| Конкурентность | 2 соединения на площадку | да |
| Джиттер между запросами | 200–800 мс, случайно | да |
| Повторы при сетевой ошибке | 2, backoff 2 с → 8 с | да |
| Реакция на `429` / `503` | пауза `Retry-After` или 15 мин, затем 2 попытки | нет |
| Реакция на `403` | **стоп-кран**: обход по площадке прерывается, состояния не обновляются, алерт разработчику | нет |
| Окно обхода | 06:00–09:30 МСК | да |
| Идентификация | стабильный `User-Agent` браузерного типа; при наличии договорённости с площадкой — с контактным суффиксом | да |

**Стоп-кран при `403` — обязательное требование.** Он реализует обещание «средства защиты площадок не затрагиваются»: при появлении блокирующей защиты система останавливается и сообщает, а не пытается её преодолеть.

**Расчёт фактической нагрузки:** L1 ≈ 30 запросов + L2 ≈ 850 + контрольные перепроверки ≈ 60 + аудитор 45 ≈ **985 запросов в сутки на три площадки**, распределённые на 3,5 часа. Это ≈ 0,08 запроса/сек суммарно и ≈ 1 запрос в 40 секунд на площадку — на порядок ниже установленного потолка.

### 5.4 Требования по площадкам (заполняется по итогам Фазы 0)

Для каждой площадки в Фазе 0 фиксируется **паспорт коннектора** — обязательный артефакт, без которого коннектор не считается готовым:

| Пункт паспорта | ПроДокторов | НаПоправку | СберЗдоровье |
|---|---|---|---|
| Способ получения листинга врачей | *Ф0* | *Ф0* | *Ф0* |
| Способ получения календаря | *Ф0* | *Ф0* | *Ф0* |
| Горизонт площадки | **14 дней (подтверждено)** | *Ф0* | *Ф0* |
| Сигнатура «карточки нет» | *Ф0* | *Ф0* | *Ф0* |
| Сигнатура «запись выключена» | *Ф0* | *Ф0* | *Ф0* |
| Сигнатура «календарь пуст» (Р1/Р2) | *Ф0* | *Ф0* | *Ф0* |
| Сигнатура «дни есть, слотов нет» (Р6) | *Ф0* | *Ф0* | *Ф0* |
| `distinguishes_empty_schedule` | *Ф0* | *Ф0* | *Ф0* |
| Стабильные внешние ID | *Ф0* | *Ф0* | *Ф0* |
| Требуется ли JS / подпись запроса | *Ф0* | *Ф0* | *Ф0* |
| Поведение при превышении частоты | *Ф0* | *Ф0* | *Ф0* |
| Ограничения `robots.txt` и соглашения | *Ф0* | *Ф0* | *Ф0* |
| Дата снятия фикстур | *Ф0* | *Ф0* | *Ф0* |

**Деградация:** если `distinguishes_empty_schedule = false`, состояния `NO_SLOTS` и `SCHEDULE_EMPTY` для этой площадки сливаются в `NO_SLOTS_UNCLASSIFIED`, в интерфейсе помечаются «причина не определима на этой площадке», алерт по ним **включён** (консервативно). Это должно быть видно оператору, а не спрятано.

## 6. Модель состояний и классификатор

**Это центральный раздел ТЗ.** Он реализует главную доработку относительно КП: разделение «врач расписан» и «расписание не выгрузилось». КП объединяет их справедливым доводом «для пациента это одно и то же» — но действия клиники в этих случаях разные, а частота первого случая такова, что без разделения раздел заполнится ложным негативом от самых востребованных врачей.

### 6.1 Множество состояний

| Состояние | Определение | Класс | Алерт по умолчанию | Соответствует разрыву (§1 в [01-RESEARCH.md](01-RESEARCH.md)) |
|---|---|---|---|---|
| `AVAILABLE` | Запись включена; есть ≥1 свободный слот в горизонте H | OK | — | норма |
| `THIN` | Запись включена; ближайший свободный слот дальше `D_ok` (3 дня), но в пределах H | OK* | — (алерт в пакете C) | загрузка |
| `NO_SLOTS` | Запись включена; календарь **содержит дни приёма**, но свободных слотов нет ни в одном | WATCH | **нет** | Р6 — врач расписан |
| `SCHEDULE_EMPTY` | Запись включена; календарь **пуст** — нет ни одного дня приёма в горизонте | BAD | **да** | Р1, Р2, Р7 — расписание не заведено или не выгрузилось |
| `BOOKING_OFF` | Карточка есть; онлайн-запись на ней не подключена | BAD | **да** | Р3, Р4 — настройки кабинета |
| `CARD_MISSING` | Карточка врача не найдена в листинге клиники | BAD | **да** | Р5 — карточка скрыта/удалена/переехала |
| `NO_SLOTS_UNCLASSIFIED` | `NO_SLOTS` и `SCHEDULE_EMPTY` неразличимы на данной площадке | BAD | **да** | деградация §5.4 |
| `UNKNOWN` | Проверка не дала однозначного ответа | — | нет (клиенту); да разработчику при устойчивости | отказ наблюдения |

**Пороги:** `H = 14` дней (ограничение ПроДокторов; на других площадках — min(H, предел площадки)), `D_ok = 3` дня. Оба настраиваются на арендатора.

### 6.2 Алгоритм классификации

```
классифицировать(raw) -> Состояние:

    если raw.card_found == False:
        вернуть CARD_MISSING

    если raw.booking_enabled == False:
        вернуть BOOKING_OFF

    если raw.fetch_failed:
        вернуть UNKNOWN

    если НЕ connector.capabilities().distinguishes_empty_schedule:
        если len(raw.free_slots) == 0:  вернуть NO_SLOTS_UNCLASSIFIED
        иначе:                          перейти к оценке глубины

    # площадка различает пустой календарь и занятые слоты
    если len(raw.schedule_days) == 0:
        вернуть SCHEDULE_EMPTY           # расписание не выгружено — ДЕФЕКТ

    если len(raw.free_slots) == 0:
        вернуть NO_SLOTS                 # дни есть, всё занято — НОРМА

    # оценка глубины
    days_to_first = min(slot.date для slot в raw.free_slots) − сегодня
    если days_to_first <= D_ok:  вернуть AVAILABLE
    иначе:                       вернуть THIN
```

### 6.3 Сохраняемые признаки (пишутся всегда, независимо от состояния)

Даже когда состояние `AVAILABLE`, замер сохраняет:

| Признак | Тип | Зачем |
|---|---|---|
| `days_to_first_slot` | int / null | Основа предиктивного алерта (v2.3) и метрики глубины |
| `free_slots_count` | int | Динамика загрузки |
| `schedule_days_count` | int | Отличает «выгрузили на 2 дня» от «выгрузили на 14» |
| `horizon_used` | int | Фактический применённый горизонт |
| `checked_at` | timestamptz | Сопоставимость замеров |
| `latency_ms` | int | Здоровье коннектора |
| `source` | enum | `http` / `browser` — какой путь дал ответ |

Эти поля стоят ноль дополнительных запросов и делают возможными версии v1.1, v2.2, v2.3 без пересбора истории. **Собирать с первого дня.**

### 6.4 Подсказка «что проверить» (в интерфейсе и в алерте)

| Состояние | Текст для оператора |
|---|---|
| `SCHEDULE_EMPTY` | Расписание не дошло до площадки. Проверьте: заведён ли график в МИС на ближайшие 2 недели; работает ли выгрузка (шина/интеграция); не выгружено ли расписание за пределы горизонта площадки |
| `BOOKING_OFF` | Онлайн-запись отключена на карточке. Проверьте кабинет площадки: включена ли запись, привязаны ли услуги и филиал |
| `CARD_MISSING` | Карточка не найдена. Проверьте: не скрыта ли карточка, не объединена ли с дублем, не сменился ли адрес. Обратитесь в поддержку площадки |
| `NO_SLOTS` | Врач расписан на весь горизонт. Это не сбой. Если поток важен — добавьте окна в расписание |
| `NO_SLOTS_UNCLASSIFIED` | Свободного времени нет. Площадка не позволяет отличить полную загрузку от несработавшей выгрузки — проверьте оба варианта |

Это превращает список проблем в список задач и напрямую сокращает MTTR у клиники.

## 7. Оркестрация обхода

### 7.1 Расписание

| Задача | Время | Периодичность |
|---|---|---|
| Основной обход | старт 06:00 МСК, окно до 09:30 | ежедневно |
| Контрольные перепроверки | по мере обнаружения BAD, +10–20 мин | внутри обхода |
| Дайджест клиенту | 09:45 МСК | ежедневно |
| Ночной аудитор (Playwright, 5 % выборка + канарейки) | 03:00 МСК | ежедневно |
| Ресинхронизация листинга и поиск новых карточек | 04:00 МСК понедельник | еженедельно |
| Недельная сводка руководителю | 10:00 МСК понедельник | еженедельно |
| Снятие истёкших заглушений | 05:30 МСК | ежедневно |

Обход выполняется в фиксированном окне: слоты меняются в течение дня, и только фиксированное время замера делает суточные значения сопоставимыми между собой.

### 7.2 Подтверждение состояний (антифлап)

**Обязательное требование.** Переход в любое BAD-состояние не принимается с первого замера.

```
замер даёт BAD:
    → контрольная перепроверка через 10–20 мин (случайно)
        совпало           → состояние ПОДТВЕРЖДЕНО
        разошлось         → третья проверка через 10–20 мин
                              большинство из трёх → подтверждено
                              большинства нет     → UNKNOWN
```

Возврат в `AVAILABLE` подтверждается тем же правилом — чтобы инцидент не «мигал» открытием и закрытием.

`UNKNOWN` **не открывает и не закрывает инцидент**. Он замораживает последнее известное состояние, помечая его «данные не обновлялись N дней». Три `UNKNOWN` подряд по одной ТМ → инцидент класса «наблюдение потеряно», алерт **разработчику**, не клиенту.

### 7.3 Канарейки — самодиагностика

**Обязательное требование.**

- Набор: 5–10 ТМ на каждую площадку, для которых достоверно известно, что запись работает. Формируются двумя путями: (а) ТМ с максимальной исторической стабильностью (≥60 дней подряд `AVAILABLE`), (б) вручную подтверждённые при приёмке.
- Канарейки проверяются в начале и в конце каждого обхода по площадке.
- **Если ≥50 % канареек площадки одновременно перешли в BAD** — считаем, что сломались мы или площадка, а не клиника:

```
обход по площадке помечается SUSPECT
    → состояния ТМ по этой площадке НЕ обновляются
    → инциденты по этой площадке НЕ открываются
    → алерты клиенту по этой площадке ПОДАВЛЯЮТСЯ
    → технический алерт разработчику: «канарейки <площадка>: 7/8 упали, обход помечен SUSPECT»
    → в дайджесте клиенту: «<Площадка>: проверка временно недоступна, данные не обновлены»
```

Это самая дешёвая защита от массового ложного алерта в системе: 30 запросов в сутки против репутации продукта.

### 7.4 Порог массовости

**Обязательное требование.** Считается после завершения обхода, до формирования уведомлений.

| Срез | Порог | Интерпретация в сообщении |
|---|---|---|
| площадка × филиал | ≥30 % ТМ среза перешли в BAD, и их ≥10 | «Похоже на сбой выгрузки расписания из МИС по филиалу» |
| площадка (вся) | ≥30 % ТМ площадки перешли в BAD, и их ≥25, **канарейки живы** | «Похоже на изменение настроек в кабинете или на стороне площадки» |
| площадка (вся) | то же, но **канарейки упали** | не сообщение клиенту, а `SUSPECT` (см. §7.3) |

При срабатывании порога индивидуальные строки по этим ТМ **не** попадают в дайджест отдельными пунктами — вместо них одно сводное сообщение со ссылкой на отфильтрованный раздел.

### 7.5 Стоп-кран и деградация

| Событие | Реакция |
|---|---|
| `403` от площадки | Обход по площадке прерван, состояния не обновлены, алерт разработчику, в дайджесте клиенту — «проверка по площадке приостановлена» |
| `429` | Пауза `Retry-After` (или 15 мин), 2 попытки, затем как `403` |
| Доля `UNKNOWN` по площадке > 20 % | Обход помечается `DEGRADED`, алерт разработчику, состояния обновляются только по успешным проверкам |
| Обход не завершился за окно | Прерывание, отметка `TIMEOUT`, алерт разработчику, состояния обновляются частично, в дайджесте — «проверено N из M» |
| Обход не запустился | Ловится внешним watchdog (healthchecks.io) → алерт разработчику |

**Требование:** ни при какой деградации система не имеет права выдать клиенту «запись пропала» по причине собственной неисправности. При сомнении — молчать и сообщать разработчику.

## 8. Инциденты и история

### 8.1 Жизненный цикл инцидента

```
AVAILABLE/THIN ──подтверждённый BAD──► ИНЦИДЕНТ ОТКРЫТ
                                        started_at = дата подтверждения
                                        state = конкретное BAD-состояние
                                        snapshot_id = доказательство
                                            │
                              смена BAD→другой BAD (напр. SCHEDULE_EMPTY→BOOKING_OFF)
                                            │  инцидент НЕ закрывается,
                                            │  пишется переход в историю состояний
                                            ▼
                                        UNKNOWN → инцидент заморожен, длительность
                                                  продолжает считаться
                                            │
                     подтверждённый AVAILABLE/THIN
                                            ▼
                                        ИНЦИДЕНТ ЗАКРЫТ
                                        ended_at, duration_days
```

**Требования:**

| | |
|---|---|
| И1 | Дата начала инцидента (`started_at`) — дата **первого подтверждённого** BAD-замера, а не дата первого сомнительного |
| И2 | `UNKNOWN`-разрывы **не** дробят инцидент на несколько. Иначе «дата пропажи» будет прыгать, а это главная цифра, которую смотрит оператор |
| И3 | Переход между разными BAD-состояниями внутри инцидента не создаёт новый инцидент, но фиксируется в истории состояний ТМ |
| И4 | Инцидент, начавшийся во время заглушения ТМ, не создаётся; после снятия заглушения открывается новый |
| И5 | `NO_SLOTS` открывает инцидент класса WATCH (виден в разделе, не алертится, не влияет на Booking Uptime в базовой формуле) |
| И6 | На момент открытия и закрытия инцидента сохраняется снапшот-доказательство |

### 8.2 История и хранение

| Данные | Срок хранения | Объём в год (900 ТМ) |
|---|---|---|
| Суточные замеры состояний | бессрочно | 328 500 строк ≈ 60 МБ |
| Инциденты | бессрочно | ~2 000 строк |
| Снапшоты на моменты перехода (усечённые до 64 КБ) | бессрочно | ~4 000 × 20 КБ ≈ 80 МБ |
| Снапшоты обычных замеров | 30 дней, затем удаление | ~500 МБ скользящих |
| Логи приложения | 14 дней | |
| Технические трассировки Playwright | 7 дней | |

Партиционирование не требуется до 10+ арендаторов. Резервное копирование БД — ежедневно, хранение 30 дней, проверка восстановления при приёмке.

## 9. Реестр врачей и сопоставление с карточками

**Недооценённая в КП работа.** Пункт 5 состава работ («настройка на реальных данных клиники») — это на 70 % именно она.

### 9.1 Источник реестра

Приоритет: выгрузка из МИС клиники (CSV/XLSX: ФИО, специальность, филиал, признак активности, внутренний ID) → при отсутствии — ручная таблица от клиники. Формат фиксируется на старте Фазы 7 и является **условием начала этапа**.

### 9.2 Алгоритм сопоставления

```
1. Получить полный листинг карточек клиники на площадке (L1) —
   даёт кандидатов с внешними ID, ФИО, специальностью, филиалом.

2. Нормализовать ФИО: нижний регистр, ё→е, схлопывание пробелов и дефисов,
   разбор форм «Фамилия И.О.» ↔ «Фамилия Имя Отчество»,
   учёт двойных фамилий.

3. Точное совпадение (фамилия + инициалы + филиал)          → автосвязка
4. Точное по фамилии+инициалам, филиал не совпал            → автосвязка с флагом «проверить филиал»
5. Нечёткое (Jaro-Winkler ≥ 0.92) + совпадение специальности → кандидат на подтверждение
6. Несколько кандидатов / однофамильцы / ноль кандидатов     → ручной разбор
```

**Ожидаемый результат:** 80–90 % автоматически, 10–20 % (30–90 карточек на три площадки) — вручную, по 1–2 минуты на карточку. Это 2–4 человеко-дня, из которых код ускоряет только первую половину.

### 9.3 Требования

| | |
|---|---|
| С1 | Связь ТМ с карточкой хранится по **внешнему ID карточки**, а не по ФИО. ФИО — только для отображения |
| С2 | Смена ФИО на площадке (замужество, опечатка) **не должна** рвать связь |
| С3 | Еженедельно проверяется существование всех связанных карточек; исчезнувшая → `CARD_MISSING`, а не молчаливое выпадение из наблюдения |
| С4 | Новые карточки в листинге, не связанные ни с кем, попадают в очередь «Новые карточки» с уведомлением администратору |
| С5 | Врач, отсутствующий в реестре И без карточек → архивируется, не создаёт инцидентов |
| С6 | Врач в реестре, для которого не найдена карточка на площадке, где клиника представлена → отдельный статус `NOT_LISTED` в отчёте о полноте покрытия, **не** инцидент |
| С7 | Один врач в нескольких филиалах → **несколько ТМ**. Единица наблюдения — «врач × филиал × площадка», а не «врач × площадка» |

**Внимание к С7:** оценка «300 врачей × 3 площадки = 900 карточек» из КП верна только при одном филиале на врача. При среднем 1,3 филиала на врача фактическое число ТМ ≈ **1 170**. Это надо уточнить на старте: от этого зависят время обхода, цена «за точку» и объём ручного сопоставления.

## 10. Уведомления

### 10.1 Каналы

| Канал | Получатели | Содержание |
|---|---|---|
| Telegram-группа клиники | Оператор, руководитель | Дайджест, срочные массовые события, недельная сводка |
| Telegram-канал разработчика | Разработчик | Технические алерты: канарейки, `SUSPECT`, `403`, деградация, расхождения аудитора, ошибки |

Разделение каналов обязательно: технические сообщения в клиентском канале обесценивают все остальные.

### 10.2 Правила отправки

| | |
|---|---|
| У1 | **Ежедневный дайджест отправляется всегда**, даже если изменений нет. Молчание неотличимо от смерти системы; дайджест — это ещё и heartbeat для клиента |
| У2 | Об одном инциденте — одно сообщение об открытии и одно о закрытии. Повторов нет |
| У3 | Долгоживущие инциденты напоминают о себе только блоком «дольше всего без записи» в дайджесте |
| У4 | При срабатывании порога массовости (§7.4) — одно сводное сообщение вместо N индивидуальных |
| У5 | Срочные сообщения отправляются только в рабочие часы (09:00–19:00 МСК, настраивается); вне окна копятся до утреннего дайджеста |
| У6 | Возвраты записи **не** отправляются отдельными сообщениями — только блоком в дайджесте (иначе шум удваивается) |
| У7 | Заглушённые ТМ не порождают уведомлений |
| У8 | При `SUSPECT`-обходе клиентские уведомления по затронутой площадке подавляются |

### 10.3 Форматы (макеты)

**Ежедневный дайджест** (09:45, всегда):

```

   Расписание не дошло до площадки
 • Петрова А. В., невролог — СберЗдоровье, Труда 12
   Онлайн-запись отключена на карточке
 • ... ещё 4

🟢 Вернулась запись: 3

⏳ Дольше всего без записи:
 • Сидоров С. С. — НаПоправку, 11 дней
 • Кузнецова М. И. — ПроДокторов, 8 дней

Доступность записи за месяц: 94,1 % (было 91,2 %)
→ Открыть раздел «Онлайн-запись»
```

**Срочное сообщение о массовом событии:**


## 14. Наблюдаемость и самодиагностика

**Обязательный раздел.** Система, которая молча перестала работать, хуже отсутствующей — она создаёт ложное чувство контроля.

| Механизм | Что ловит | Куда сообщает |
|---|---|---|
| **Канарейки** (§7.3) | Поломку коннектора или изменение площадки | Технический алерт, `SUSPECT` |
| **Ночной аудитор** | Расхождение HTTP-пути и браузерного рендера на выборке 5 % | Технический алерт при расхождении >2 точек |
| **Внешний watchdog** (healthchecks.io) | Обход не запустился вообще | Технический алерт |
| **Sentry** | Исключения, деградация, изменения структуры ответов | Технический алерт |
| **Журнал обходов** | Длительность, число проверок, распределение состояний, доля `UNKNOWN`, число `403`/`429` | Таблица + сводка в техканал |
| **Контроль дрейфа** | Резкое изменение распределения состояний по площадке день ко дню (>3σ от 30-дневного среднего) | Технический алерт |
| **Проверка свежести данных** | ТМ, не проверявшаяся >36 ч | Красная метка в интерфейсе + технический алерт |

Каждый прогон обхода записывает в таблицу `crawl_runs` полную сводку. Разбор любого инцидента начинается с неё.

## 15. Безопасность и персональные данные

| | Требование |
|---|---|
| Б1 | Система **не собирает** данные о пациентах и о занятых приёмах. Из календаря извлекаются только даты и время **свободных** слотов и их количество (п. 11.7 договора) |
| Б2 | Обрабатываемые данные о врачах (ФИО, специальность, филиал) — **общедоступные**, опубликованные самой клиникой на площадках. Правовой режим и основания — [08-RISKS-LEGAL.md](08-RISKS-LEGAL.md) |
| Б3 | Реестр врачей, полученный от клиники, обрабатывается на основании **поручения на обработку** от клиники как оператора ПДн (ст. 6 ч. 3 152-ФЗ). Поручение оформляется до передачи реестра |
| Б4 | Серверы и резервные копии размещаются на территории РФ |
| Б5 | Доступ к разделу — по ролям существующего дашборда; отдельных учётных записей не создаётся |
| Б6 | Секреты (токены Telegram, доступ к БД, ключи площадок) — в переменных окружения с ограниченными правами на файл, не в репозитории. Ротация при смене состава исполнителей |
| Б7 | Все изменяющие действия — в журнал аудита с автором, временем и причиной |
| Б8 | Снапшоты проверяются на отсутствие ПДн пациентов перед сохранением; поля, не относящиеся к свободным слотам, вырезаются на этапе нормализации, **до** записи на диск |
| Б9 | Трафик к площадкам и в Telegram — только TLS; проверка сертификатов не отключается ни при каких обстоятельствах |
| Б10 | При получении от площадки требования прекратить сбор — сбор по этой площадке останавливается немедленно, до разрешения вопроса с правообладателем |

**Б8 — не формальность.** Календарь площадки может содержать в ответе поля, не относящиеся к свободным слотам. Вырезание должно происходить в нормализаторе коннектора, до попадания данных в БД и в снапшот.

## 16. Тестирование

| Уровень | Содержание | Где выполняется |
|---|---|---|
| **Golden-фикстуры коннекторов** | Для каждой площадки — сохранённые реальные ответы для **каждого** состояния §6.1 (`AVAILABLE`, `THIN`, `NO_SLOTS`, `SCHEDULE_EMPTY`, `BOOKING_OFF`, `CARD_MISSING`, битый ответ). Тест: фикстура → ожидаемое состояние | CI, на каждый коммит |
| **Тесты классификатора** | Полное покрытие ветвей §6.2, включая деградацию `distinguishes_empty_schedule=false` | CI |
| **Тесты движка инцидентов** | Сценарии: флап, `UNKNOWN`-разрыв, смена BAD→BAD, заглушение во время инцидента, возврат | CI |
| **Тесты политики уведомлений** | Порог массовости, дедупликация, тихие часы, подавление при `SUSPECT` | CI |
| **Тесты сопоставления** | Нормализация ФИО, однофамильцы, смена фамилии, двойные фамилии, «ё» | CI |
| **Контрактные тесты (живые)** | Раз в сутки: обращение к площадке и сверка структуры ответа со схемой. Изменение → технический алерт **до** того, как сломается классификация | Прод, ежедневно |
| **Нагрузочная проверка** | Обход 1 200 ТМ в границах лимитов, замер длительности | Перед приёмкой |
| **Проверка восстановления** | Восстановление БД из бэкапа на чистом хосте | Перед приёмкой |

**Golden-фикстуры — важнейший артефакт проекта.** Они позволяют чинить коннектор за часы вместо дней и делают возможной безопасную работу с Claude Code: агент правит парсер, тесты немедленно показывают, не сломал ли он классификацию. Снимать фикстуры в Фазе 0 и обновлять при каждом ремонте.

## 17. Конфигурация и развёртывание

|---|---|

- VPS в РФ, Docker Compose: `api`, `worker`, `scheduler`, `postgres`, `playwright`

- systemd-юнит на compose, автоперезапуск
- Логи в `journald` + Sentry
- Бэкап БД: `pg_dump` по расписанию в объектное хранилище РФ, шифрование, хранение 30 дней
- Раскатка: `git pull` → миграции → перезапуск; при изменении коннектора — обязательный прогон golden-тестов **до** раскатки

### 17.3 Runbook (обязательный артефакт)

Документ с процедурами, готовый к передаче: смена механики площадки, `403`/блокировка, обход не запустился, массовый `UNKNOWN`, расхождение аудитора, восстановление из бэкапа, добавление врача/филиала/площадки, изменение порогов. Подробно — [08-RISKS-LEGAL.md §4](08-RISKS-LEGAL.md).

## 18. Приёмка

### 18.1 Условия начала приёмки

- Все ТМ заведены и сопоставлены; отчёт о полноте покрытия сформирован
- Проведён **тихий прогон ≥14 суток**: система работает, алерты клиенту отключены, пороги откалиброваны
- Runbook и golden-фикстуры переданы

### 18.2 Критерии приёмки

| # | Критерий | Метод | Порог |
|---|---|---|---|
| П1 | **Точность состояний** | Ручная сверка выборки **60 ТМ** (по 20 на площадку, стратифицированно: 10 в состоянии `AVAILABLE`, 10 в BAD) с тем, что видит пациент на сайте площадки. Сверка выполняется **в течение 2 часов** после обхода | Совпадение **≥95 %** |
| П2 | **Ложноположительные** | Из той же выборки: система сказала BAD, а запись есть | **≤2 %** (≤1 случай из 60) |
| П3 | **Полнота покрытия** | Отчёт о сопоставлении | **≥98 %** врачей реестра сопоставлены на каждой площадке, где клиника представлена; остальные — в отчёте с причиной |
| П4 | **Стабильность наблюдения** | Журнал обходов за 14 суток тихого прогона | Обход завершён успешно **≥14 из 14** суток; средняя доля `UNKNOWN` **≤3 %** |
| П5 | **Своевременность** | Журнал обходов и отправок | Обход завершается до 09:30 МСК, дайджест приходит до 10:00 — **14 из 14** суток |
| П6 | **История и дата пропажи** | Проверка на 10 ТМ с известной историей | Дата начала инцидента совпадает с фактом; `UNKNOWN`-разрывы не дробят инцидент |
| П7 | **Раздел и фильтры** | Чек-лист по §11 | Все фильтры работают, сортировка по умолчанию корректна, ссылки открываются |
| П8 | **Выгрузка XLSX** | Формирование по трём разным фильтрам | 4 листа, соответствие фильтрам, лист параметров заполнен, файл открывается в Excel и LibreOffice |
| П9 | **Уведомления** | Наблюдение за 14 суток + инъекция тестового массового события | Дайджест ежедневно; массовое событие даёт **одно** сообщение; повторов по одному инциденту нет |
| П10 | **Самодиагностика** | Инъекция сбоя: искусственная поломка коннектора на тестовом контуре | Канарейки срабатывают, обход помечен `SUSPECT`, клиентские алерты подавлены, технический алерт отправлен |
| П11 | **Заглушение** | Функциональная проверка | Заглушение убирает ТМ из алертов, списка и знаменателя Booking Uptime; автоснятие по дате работает |
| П12 | **Соблюдение лимитов** | Журнал запросов за сутки | Ни одного превышения 1 запрос/сек на площадку; ни одного `403`, вызванного нашей частотой |
| П13 | **Восстановление** | Восстановление БД из бэкапа на чистом хосте | Данные целы, система стартует |

### 18.3 Методика сверки для П1/П2 (протокол)

1. Сразу после обхода выгрузить срез 60 ТМ (стратифицированная случайная выборка).
2. По каждой открыть карточку врача на площадке в браузере без авторизации, в режиме инкогнито.
3. Зафиксировать: есть ли кнопка записи; открывается ли календарь; есть ли хоть один свободный слот в ближайшие 14 дней; дата ближайшего слота.
4. Сравнить с состоянием системы. Расхождение — с указанием класса: ложноположительное (сказали BAD, запись есть) / ложноотрицательное (сказали OK, записаться нельзя) / ошибка класса (BAD, но другой).
5. Ложноположительные разбираются поштучно и исправляются **до** подписания акта. Ошибки класса — фиксируются, порог 5 %.
6. Протокол сверки прикладывается к акту.

Пункт 3 выполняется **в течение 2 часов** после обхода: слоты меняются в течение дня, и сверка через сутки методологически некорректна. Это условие фиксируется в акте.
