# 06. План внедрения и методика разработки

Исполнитель — один человек + Claude Code. План построен так, чтобы **человеко-зависимые фазы шли первыми и параллельно с ожиданием заказчика**, а машинно-ускоряемые — плотным блоком.

---

## 1. Нулевой этап: до первой строчки кода

Пять вещей, каждая из которых способна обнулить проект, если сделать её позже.

| # | Действие | Почему до старта | Срок |
|---|---|---|---|
| 0.1 | **Зафиксировать права на ПО** в допсоглашении: исключительные права у исполнителя, заказчику — неисключительная лицензия | По умолчанию ст. 1296 ГК РФ отдаёт результат заказчику. Без этой строки продукт нельзя продать второй раз никогда ([02-PRODUCT.md §2а](02-PRODUCT.md)) | 1 день, параллельно |
| 0.2 | **Получить реестр врачей** от клиники: ФИО, специальность, филиал, признак активности, ID в МИС | Это блокирующий вход для Фазы 7. Запрашивать в первый день — получают обычно через 1–2 недели | запрос в день 1 |
| 0.3 | **Уточнить единицу мониторинга**: сколько врачей ведут приём более чем в одном филиале | От этого зависит фактическое число ТМ (900 или 1 170+), время обхода, цена «за точку» и объём ручного сопоставления ([04-TZ.md §9, С7](04-TZ.md)) | запрос в день 1 |
| 0.4 | **Определить площадку для раздела**: есть ли доступ к коду существующего дашборда, какой стек | Разница в оценке 2–3 человеко-дня; влияет на выбор ветки в [01-RESEARCH.md §5](01-RESEARCH.md) | день 1 |
| 0.5 | **Назначить ответственного на стороне клиники** — конкретного человека, который получает алерты и реагирует | Без него метрика MTTR недостижима, а на приёмке некому подтверждать сверку. Продукт без адресата не используется | день 1 |

## 2. Фазы

Обозначения: **[Ч]** — человеко-зависимая, Claude Code почти не ускоряет; **[М]** — машинно-ускоряемая; **[О]** — зависит от ожидания заказчика.

### Фаза 0 · Рекогносцировка трёх площадок **[Ч]** — 6 чел-дней (P50)

Главный источник неопределённости во всём проекте. Выполняется вручную, в DevTools, по каждой площадке.

**Работы:**
1. Открыть карточку врача клиники, записать все сетевые запросы при рендере и при открытии виджета записи.
2. Найти листинг врачей клиники (L1) и запрос календаря (L2). Проверить пагинацию, фильтр по филиалу.
3. **Снять фикстуры для всех семи состояний** ([04-TZ.md §16](04-TZ.md)): найти на площадке живые примеры доступного врача, врача без слотов, врача без записи, несуществующей карточки; для `SCHEDULE_EMPTY` — при необходимости попросить клинику временно снять расписание с одного тестового врача.
4. Определить, отличим ли пустой календарь от полностью занятого — `distinguishes_empty_schedule`.
5. Проверить стабильность внешних ID: те же ID через сутки.
6. Проверить поведение при повышенной частоте (аккуратно, с большим шагом), наличие `Retry-After`.
7. Прочитать `robots.txt` и пользовательское соглашение площадки, зафиксировать ограничения.
8. Оценить партнёрский API СберЗдоровья как альтернативу ([01-RESEARCH.md §4.3](01-RESEARCH.md)).
9. Заполнить **паспорт коннектора** по каждой площадке.

**Definition of Done:** три заполненных паспорта + 21 golden-фикстура (7 состояний × 3 площадки) в репозитории + решение по архитектуре каждой площадки (A1/A2) + зафиксированные ограничения из соглашений.

**Риск фазы:** если СберЗдоровье потребует браузера и подписи запроса — +3–5 чел-дней. Заложено в P80.

---

### Фаза 1 · Каркас **[М]** — 1 чел-день

Репозиторий, `CLAUDE.md`, Docker Compose, PostgreSQL, модели по [05-DATA-MODEL.md](05-DATA-MODEL.md), Alembic-миграции, конфиг из БД, логирование, Sentry, healthchecks.io, CI (ruff + mypy + pytest).

**DoD:** `docker compose up` поднимает всё; миграции применяются; CI зелёный на пустых тестах; Sentry принимает тестовое исключение.

---

### Фаза 2 · Классификатор **[М]** — 1,5 чел-дня

**Делается до коннекторов**, на golden-фикстурах из Фазы 0. Реализация [04-TZ.md §6.2](04-TZ.md) + полное покрытие тестами всех ветвей, включая деградацию.

**DoD:** 21 фикстура → 21 ожидаемое состояние, тесты зелёные. Ни одной ветви без теста.

Порядок «классификатор раньше коннекторов» неочевиден, но правилен: он фиксирует контракт, и коннекторы пишутся под известную цель, а не наоборот.

---

### Фаза 3 · Три коннектора **[М]** — 4 чел-дня

По паспортам и фикстурам. Общий интерфейс [05-DATA-MODEL.md §3](05-DATA-MODEL.md). Транспорт с лимитами, джиттером, повторами. Playwright-fallback общий для всех.

**DoD:** каждый коннектор проходит golden-тесты; на живой площадке успешно снимает состояние по 20 реальным ТМ; соблюдает лимит 1 запрос/сек; `raw_payload` очищен от посторонних полей (инвариант К2).

---

### Фаза 4 · Оркестратор обхода **[М]** — 3 чел-дня

Очередь ТМ, эскалация L1→L2, ограничение частоты и конкурентности на площадку, повторы, стоп-кран `403`/`429`, подтверждение 2-из-3, канарейки, `SUSPECT`/`DEGRADED`/`TIMEOUT`, журнал `crawl_runs`.

**DoD:** полный обход по всем ТМ завершается за ≤60 мин; журнал заполняется; инъекция искусственного `403` останавливает обход по площадке; инъекция «упавших канареек» помечает обход `SUSPECT`.

---

### Фаза 5 · Движок инцидентов **[М]** — 2 чел-дня

Открытие/закрытие, склейка через `UNKNOWN`, переходы BAD→BAD, взаимодействие с заглушениями, массовые события и пороги.

**DoD:** тесты покрывают все шесть сценариев [04-TZ.md §8.1](04-TZ.md); `UNKNOWN`-разрыв не дробит инцидент; порог массовости срабатывает на синтетических данных.

---

### Фаза 6 · Уведомления **[М]** — 2 чел-дня

Шаблоны Jinja2, политика (дедуп, тихие часы, подавление при `SUSPECT`), два канала, inline-кнопки заглушения, дайджест/массовое/недельное/технические.

**DoD:** все девять шаблонов рендерятся на синтетических данных; дедупликация не даёт повторов; массовое событие даёт одно сообщение вместо N; технические сообщения не попадают в клиентский канал.

---

### Фаза 7 · Реестр и сопоставление **[Ч]** **[О]** — 4 чел-дня

Загрузка реестра, нормализация ФИО, автосопоставление, интерфейс ручного разбора, очередь новых карточек, отчёт о покрытии.

Из четырёх дней примерно **два — ручная сверка неоднозначных карточек**. Не ускоряется.

**DoD:** отчёт о покрытии показывает ≥98 % сопоставления на каждой площадке; несопоставленные врачи перечислены с причинами; повторный запуск сопоставления идемпотентен.

---

### Фаза 8 · Раздел дашборда и XLSX **[М]** — 4 чел-дня

API [05-DATA-MODEL.md §4](05-DATA-MODEL.md), сводка, таблица с виртуализацией, фильтры с сохранением в URL, карточка ТМ с лентой истории и доказательствами, заглушение, четырёхлистовая выгрузка.

**DoD:** чек-лист [04-TZ.md §11](04-TZ.md) пройден; открытие ≤1,5 с на 1 200 ТМ; XLSX открывается в Excel и LibreOffice, лист параметров заполнен; мобильная вёрстка читаема.

---

### Фаза 9 · Наблюдаемость и эксплуатация **[М]** — 1,5 чел-дня

Ночной аудитор, контроль дрейфа, проверка свежести, watchdog, бэкапы с проверкой восстановления, systemd, **runbook**.

**DoD:** runbook покрывает девять сценариев [04-TZ.md §17.3](04-TZ.md); восстановление из бэкапа проверено на чистом хосте; аудитор ловит подсунутое расхождение.

---

### Фаза 10 · Тихий прогон и калибровка **[Ч]** — 3 чел-дня, растянуто на 14 календарных

Система работает в проде, клиентские алерты **отключены**. Ежедневно: разбор ложных срабатываний, калибровка порогов (через настройки, без деплоя), пополнение канареек, добор фикстур на нестандартные ответы.

**Это фаза, которую все сокращают и все потом жалеют.** Именно здесь FPR падает с 10–15 % до ≤2 %.

**DoD:** 14 суток подряд успешный обход; доля `UNKNOWN` ≤3 %; на контрольной выборке 30 ТМ ложноположительных нет; пороги зафиксированы.

---

### Фаза 11 · Приёмка **[Ч]** **[О]** — 3 чел-дня, растянуто на 5–10 календарных

Протокол сверки [04-TZ.md §18.3](04-TZ.md) на выборке 60 ТМ, прогон 13 критериев, устранение расхождений, передача runbook и инструкции оператора, обучающая сессия.

**DoD:** акт подписан; протокол сверки приложен; ответственный на стороне клиники обучен и получает алерты.

## 3. Порядок и параллелизм

```
Неделя 1     0.1–0.5 (запросы клиенту)  ┃ Фаза 0: рекогносцировка ПД, НП
Неделя 2     ожидание реестра  ← [О]    ┃ Фаза 0: СЗ + паспорта + фикстуры
Неделя 3                                ┃ Фазы 1, 2, 3 (каркас, классификатор, коннекторы)
Неделя 4                                ┃ Фазы 4, 5 (оркестратор, инциденты)
Неделя 5     реестр получен             ┃ Фазы 6, 7 (уведомления, сопоставление)
Неделя 6                                ┃ Фазы 8, 9 (раздел, XLSX, эксплуатация)
Неделя 7–8   ┏━━━━━━━━━━━━━━━━━━━━━━━━━━┫ Фаза 10: тихий прогон, 14 суток
Неделя 9     ┗━ приёмка ← [О]           ┃ Фаза 11
```

**Критический путь:** Фаза 0 → 1 → 2 → 3 → 4 → 10 → 11. Фазы 7 и 8 идут параллельно и не удлиняют проект, если реестр получен к неделе 5.

**Главный риск графика — не разработка, а Фаза 0 и получение реестра.** Обе начинать в первый день.

## 4. Методика работы с Claude Code

Раздел практический: что реально ускоряется, что нет, и как не получить правдоподобно выглядящий, но неработающий код.

### 4.1 Коэффициенты ускорения по типам работ

| Тип работы | Ускорение | Комментарий |
|---|---|---|
| Модели, миграции, CRUD, роутеры FastAPI | **×4–5** | Идеальный случай: контракт известен, код шаблонный |
| Тесты по готовым фикстурам | **×4–5** | Дайте фикстуру и ожидаемый результат — тесты пишутся мгновенно |
| Выгрузка XLSX, шаблоны сообщений | **×4** | Много рутины, мало логики |
| Таблица с фильтрами, виртуализация | **×3** | |
| Классификатор, движок инцидентов | **×2** | Логика тонкая; агент пишет быстро, но проверять надо самому |
| Коннекторы **при наличии фикстур** | **×2–2,5** | |
| Коннекторы **без фикстур** | **×0,3 — вредно** | См. 4.3 |
| Рекогносцировка в DevTools | **×1** | Не ускоряется |
| Сверка сопоставления, калибровка порогов, приёмка | **×1** | Не ускоряется |

Отсюда и берётся цифра «46 % работ не ускоряются» — она и делает срок 8–9 недель, а не 3.

### 4.2 `CLAUDE.md` для этого репозитория

```markdown
# Booking Monitor

## Инварианты, которые нельзя нарушать
- Коннектор НИКОГДА не возвращает состояние (point_status). Только сырые факты
  из dataclasses в connectors/base.py. Классификация — только в classify.py.
- Пороги, окна, лимиты — НИКОГДА не константы в коде. Только tenants.settings.
- Любое изменение classify.py, incidents.py, notify/policy.py — только вместе
  с тестом. Прогон pytest обязателен перед тем, как сказать «готово».
- raw_payload очищается от полей, не относящихся к свободным слотам,
  ДО возврата из коннектора. Данные о занятых приёмах не должны попадать
  в БД никогда.
- tenant_id обязателен в каждом запросе к БД. Ни одного глобального SELECT.
- Не добавлять обход средств защиты площадок. При 403 — стоп-кран,
  а не подбор обходного пути.

## Как писать коннектор
1. Фикстура из tests/fixtures/<платформа>/ — единственный источник правды
   о формате ответа. НЕ УГАДЫВАТЬ структуру и НЕ ПРИДУМЫВАТЬ эндпоинты.
2. Если нужного случая нет в фикстурах — остановиться и сказать об этом,
   а не сочинять.
3. Тест на каждое из 7 состояний.

## Проверка перед «готово»
ruff check . && mypy src && pytest -q
```

### 4.3 Главный антипаттерн: коннектор без фикстур

Если попросить агента «напиши парсер расписания ПроДокторов», он выдаст правдоподобный код с выдуманными URL, выдуманными именами полей и выдуманной логикой. Код будет выглядеть профессионально и не будет работать. Хуже: на отладку уйдёт больше времени, чем на написание с нуля, потому что придётся сначала разобраться, что именно придумано.

**Правило: сначала фикстура, потом код.** Снимите реальный ответ в DevTools, положите в `tests/fixtures/`, и только тогда просите написать парсер под неё. Это и есть причина, по которой Фаза 0 идёт первой и не сокращается.

### 4.4 Дисциплина сессий

| Правило | Зачем |
|---|---|
| Одна фаза — одна сессия | Контекст остаётся сфокусированным, легче откатывать |
| Коммит после каждой зелёной фазы, ветка на фазу | Есть куда откатиться |
| Тесты — контракт, а не проверка постфактум | Пишите ожидаемое поведение до реализации, особенно для `classify.py` |
| Читать диффы в `classify.py`, `incidents.py`, `notify/policy.py` глазами | Три файла, где ошибка стоит доверия клиента. Остальное можно принимать по тестам |
| Не давать агенту доступ к проду | Обходы, миграции, рассылки — вручную |
| Golden-фикстуры не менять «чтобы тест прошёл» | Единственный способ поймать регресс коннектора. Меняются только при подтверждённой смене формата площадки |

### 4.5 Где Claude Code даёт наибольший выигрыш именно здесь

1. **Тесты движка инцидентов.** Шесть сценариев с датами, склейками и `UNKNOWN`-разрывами — нудно писать руками, идеально для агента, и именно эти тесты потом ловят регрессы.
2. **Четырёхлистовая выгрузка XLSX** с форматированием — час вместо дня.
3. **Ремонт коннектора при смене площадки.** Свежая фикстура + существующие golden-тесты + агент = ремонт за 2–3 часа вместо дня. Это напрямую снижает себестоимость сопровождения ([02-PRODUCT.md §3.2](02-PRODUCT.md)) и делает подписную модель прибыльной.
4. **Отчёт о покрытии и интерфейс ручного разбора** — рутина, которую иначе легко отложить и не сделать.
